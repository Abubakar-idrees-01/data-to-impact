# 2. BM25: keyword search done properly

## Intuition
BM25 ranks chunks by how well they match the query's **words**. It improves on "count the matching words"
with three ideas:

1. **Rare words matter more** (IDF). In a marketing course "marketing" is everywhere and tells you nothing;
   "backlinks" is rare and tells you a lot.
2. **Repetition helps, with diminishing returns** (TF saturation). Mentioning "SEO" 3 times is a better sign
   than once, but 30 times is not ten times better than 3.
3. **Long chunks shouldn't win just by being long** (length normalisation).

## The formula
For query terms *t* and a chunk *d*:

```
score(d) = Σ  IDF(t) · tf(t,d) · (k1 + 1)
           t  ───────────────────────────────────────────
              tf(t,d) + k1 · (1 − b + b · |d| / avgdl)

IDF(t) = ln( (N − df(t) + 0.5) / (df(t) + 0.5) + 1 )
```

| Symbol | Meaning | Our value |
|---|---|---|
| `tf(t,d)` | times term t appears in chunk d | |
| `df(t)` | number of chunks containing t | |
| `N` | total chunks | |
| `|d|`, `avgdl` | chunk length, average chunk length (in tokens) | |
| `k1` | saturation: how fast extra repetitions stop helping | 1.5 |
| `b` | how strongly to penalise long chunks (0 = not at all, 1 = fully) | 0.75 |

The `+1` inside the log is Lucene's variant: it keeps IDF positive even for words in more than half the chunks.

**Worked example:** query "backlinks", N = 100 chunks, the word is in 4 of them.
IDF = ln((100 − 4 + 0.5)/(4 + 0.5) + 1) = ln(22.4) ≈ 3.11. A chunk of average length with tf = 2 scores
3.11 · 2 · 2.5 / (2 + 1.5) ≈ 4.44. A chunk with tf = 1 scores 3.11 · 2.5 / 2.5 = 3.11. So twice the
mentions gives 43% more score, not 100% more. That is saturation at work.

## Our implementation ([`bm25.py`](../../src/studyrag/bm25.py), [`text.py`](../../src/studyrag/text.py))
- **Tokenizer:** lowercase → words → drop stopwords ("the", "is", ...) → **stem** ("advertising",
  "advertised", "advertisement" → "advertis").
- **Inverted index:** `term → [(chunk_id, tf), ...]`. A query only touches chunks containing at least one
  query term, instead of scanning every chunk.
- **Vectorised scoring:** per query term, NumPy adds that term's contribution to all matching chunks at once.
- **Tested** against a hand-computed score in [`tests/test_retrieval_core.py`](../../tests/test_retrieval_core.py).

## Strengths and weaknesses
| BM25 is great at | BM25 fails at |
|---|---|
| exact terms, names, acronyms, codes ("CPC", "GA4", "DSGE-294") | synonyms ("buyers" vs "customers") |
| being fast, explainable and needing no model | paraphrased questions |
| rare technical vocabulary | understanding negation or intent |

The weaknesses are exactly what vector search is good at, which is why we combine both
(→ [hybrid search](04-hybrid-search-rrf.md)).

## Interview questions
- *Why is IDF logarithmic?* So a word that is 10× rarer is worth a bit more, not 10× more.
- *What happens with b = 0?* No length normalisation: long chunks get unfairly high scores.
- *Why stem?* To match word variants. The cost is occasional false matches ("organ" vs "organic").
- *Is BM25 obsolete now that we have embeddings?* No. Hybrid search beats either alone on most benchmarks,
  and BM25 is unbeatable for exact identifiers.
