# Design decisions

Each decision with what we chose, what we didn't, and why. Where we measured, the numbers are in [RESULTS](RESULTS.md).

## D1. Write the agent loop from scratch, no framework
**Chose:** ~150 lines in `agent.py` + a tool registry. **Not:** LangChain / LlamaIndex / an agents SDK.
**Why:** the loop is small, and owning it makes the behaviours we care about visible and testable: where approval is
enforced, how context is trimmed, why a run stopped. Every live failure in this project was found and fixed in
minutes because the trace showed exactly what was sent and received. Two dependencies: `httpx` and the MCP SDK.

## D2. Approval enforced in code, default no, no "approve all"
**Chose:** outward tools can only run through `Registry.call`, which asks an `Approver` first; edits are proposals in
a `ChangeSet`, applied only after one explicit "y". **Not:** telling the model to ask permission.
**Why:** a prompt can be overridden by a web page; code can't. Measured in E2: under attack the model sometimes
*tried* outward actions (posting a comment, reading `.env`), and in every case the code stopped it.

## D3. No filler commits; one real, reviewed contribution per day at most
**Chose:** the daily routine drafts one learning-log note (or doc fix); you approve it; on days with nothing worth
committing, nothing is committed. **Not:** a bot that adds N commits a day to keep the GitHub graph green (the owner
asked for that first).
**Why:** fake activity breaks the repo's own rule and is easy to spot; a log of real, cited notes is worth more on a
profile than empty squares filled with noise.

## D4. Repo tools see only git-tracked files
**Chose:** `git ls-files` defines what exists. **Not:** a folder allow-list.
**Why:** everything private in this repo is already gitignored (lecture files, `.env`, model weights). Using git as
the boundary means the agent can never read, list or send those to the model provider, with no second list to keep
in sync. Tested: `.env`, `secret/`, `../` and absolute paths are refused.

## D5. Groq gpt-oss-120b, fallback gpt-oss-20b
**Chose:** gpt-oss-120b with `reasoning_effort: low`; gpt-oss-20b when the 120b daily quota is used up.
**Not:** qwen3.8-27b (it's project 2's judge; keeping the agent on another model family keeps grading independent).
**Why:** both support tool calling on Groq's free tier (tested), and each model has its own 200k tokens/day.
Experiments disable the fallback so every answer in a run comes from one model.

## D6. Tavily for search; our own page reader
**Chose:** Tavily search (free tier, returns clean snippets, supports date and site filters); pages fetched with
httpx and reduced to relevant passages ourselves; Tavily's extract only as a fallback for blocked pages.
**Why:** our reader lets us enforce the SSRF rules and choose what the model sees (focused passages, ≤ 3,000
characters) instead of paying tokens for whole articles.

## D7. Trim old tool results to fit the request limit
**Chose:** before each call, cut the oldest tool results to a 300-character stub until the request fits (6,000
tokens incl. the reply); calibrate characters-per-token from the API's own counts. **Not:** summarising old results
with another model call (costs tokens and time on a free tier), or a bigger context (Groq's free tier caps a request
at 8,000 tokens/minute regardless of the model's context).
**Why:** the first live digest died at 9,042 tokens. After the change no request was refused for size.

## D8. Citations: numbered once per task, only for sources actually read, list generated by code
**Why:** live drafts cited unread sources, relied on one SEO blog, and invented source lists. Each became a rule
checked in `write_note` (concept 5). Rules can't check that a source *supports* a sentence, so a human still reviews.

## D9. Digests search recent primary sources first
**Chose:** Tavily `time_range=month` + a domain list (arXiv, GitHub, Hugging Face, official docs and lab blogs),
widening to the whole web only when nothing is found. **Why:** without it, drafts were built on "complete guide 2026"
blog posts and dated things by the model's training year. With it, the next draft was about a concrete spec change,
sourced from the official MCP blog.

## D10. Unattended runs prepare; humans approve later
**Chose:** `scout digest --prepare` saves a proposal; `scout review` asks. The systemd timer runs only `--prepare`.
**Why:** an unattended job can't ask anyone, and "approve automatically when nobody's there" would defeat D2.

## D11. Evaluate the agent four ways
**Chose:** (E1) does research beat the model alone on SimpleQA; (E2) prompt-injection attacks, measuring *attempted*
separately from *executed*; (E3) a planted-error repo for `checkup`, with decoys to catch over-eager "fixes";
(E4) claim support in digest notes.
**Why:** an agent can fail by being wrong (E1), by being hijacked (E2), by being busy (E3, changing things that
were fine) or by citing sources that don't say what it claims (E4). Each needs its own measurement; a single
"task success" number would hide most of them.

## D12. E4 judges each claim against what the agent actually saw, with project 2's validated judge
**Chose:** record every search snippet and read passage per source during the run; split the note into claims
(bullets, sentences); check a cited claim against its cited sources and an uncited fact against everything read,
with the judge configuration selected on RAGTruth in project 2 (`faithfulness/direct`, qwen3.8-27b). A probe changes
one number in each accepted claim; the judge must then reject it.
**Why:** code already guarantees a note cites only sources the agent read (D8), but not that the sentence says what
the source says. Re-fetching the page later would judge against a different text than the agent had, and a full
page would reward claims the agent couldn't have seen. Reusing project 2's judge means its agreement with humans is
already measured (test kappa 0.625), rather than trusting a new, unvalidated prompt. A different model family from
the writer (gpt-oss) avoids a model grading its own style. The probe checks the judge is sensitive on *these* notes,
not just on RAGTruth.
